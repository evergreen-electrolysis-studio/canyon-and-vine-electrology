## Source and build

`app/evergreen/page.tsx` is the new authoring route. It starts from the approved
Design 09 and reuses its unchanged CSS, images, rates and form components. The
exporter renders that route as the **public homepage `/`**, not `/evergreen/`.
Historical source and published snapshots stay protected by the existing
export manifest.

```sh
pnpm run build:evergreen
pnpm run preview:evergreen
```

The preview exports to ignored `out/evergreen/`. It is excluded from indexing
using page metadata and HTTP headers. Its form uses a public Turnstile test key
and a same-origin `/__preview__/request` endpoint that has no delivery backend.
Use fictional inputs; a preview submission must not claim a real signup or send
email. The unchanged production form controller can be tested for validation
and failure recovery against this artifact.

Run `pnpm test` for the historical checks, frozen hashes, form/Worker regressions
and new export checks. The website preview should also be checked in a browser
at desktop/mobile widths and through the local static-assets runtime; verify a
missing URL returns a real HTTP 404.

## Production builds and deployment

Use the Node version in `.node-version` and the package manager version in
`package.json`. Build and check changed source before exporting production:

```sh
pnpm test
pnpm run lint
node scripts/export-evergreen.mjs --production
pnpm exec wrangler deploy --config cloudflare/website/wrangler.production.jsonc
```

Production output is separate in `out/evergreen-production/`; its indexing
directives and form configuration are intended for the live domain. The preview
Wrangler configuration does **not** deploy that directory. Always pass the
explicit production `--config` path: automatic framework discovery could select
the Vinext server build instead of this static artifact.

The custom-domain binding `evergreenelectrolysisstudio.com → evergreen-website`
is managed in the Cloudflare dashboard. Keep `route` and `routes` absent from
the production Wrangler configuration and retain `workers_dev: false` and
`preview_urls: false`. Cloudflare documents this routing ownership pattern;
deploying new assets should preserve the dashboard-managed binding without
requiring broader CLI zone permissions. Do not add a route array as a routine
configuration cleanup. See [Wrangler source-of-truth guidance](https://developers.cloudflare.com/workers/wrangler/configuration/#source-of-truth).

After deployment, verify the apex HTTPS response and served artifact, canonical
and indexing metadata, required assets, an actual HTTP 404 for a missing path,
and the HTTP/`www` redirects with path and query preserved. Repeat real
form-to-inbox verification when a change affects delivery; a local mock or
success animation alone does not establish delivery.

Do not point Cloudflare at the whole repository, `dist/`, or `github-pages/`.
Publish only the new static artifact. Its real 404, sitemap, robots directives
and root-relative assets are generated by `scripts/export-evergreen.mjs`.
No health-history or consent records belong in this public artifact.

The website retains the existing owner-approved licensure statement and studio
facts. Their source approval is not independent license verification. Remaining
factual checks in the project research are still open; publication does not
complete them or establish readiness to provide treatment.

## Repository and automatic deployment

`.github/workflows/ci.yml` replaces the old Pages workflow. On pull requests,
pushes to `main`, and manual runs, its `checks` job installs locked dependencies,
runs `pnpm test` and lint, then explicitly exports production static assets.
It saves only `out/evergreen-production/` as a seven-day workflow artifact.
These checks have read-only repository permissions and no Cloudflare token.

After successful checks, a separate `deploy` job runs **only for a push to
`main` or a manual run selected on `main`**. Pull requests and manual runs on
other branches cannot enter it. The job uses the GitHub `production` environment,
downloads the artifact from that same workflow run, and deploys it with the
explicit production Wrangler configuration. It does not rebuild the site.
Only the final deployment step receives `CLOUDFLARE_API_TOKEN`; a missing token
fails deployment clearly while the completed checks retain their result.
Production runs are not canceled by a newer push during deployment.

Use GitHub Actions with an **account-owned token limited to the existing
`evergreen-website` Worker**. Cloudflare's native Workers Builds currently accepts
user API tokens rather than account tokens, so it is not the selected path.
Do not enable a second native deployment pipeline for this Worker. See
[Workers Builds token configuration](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/).

The owner created the scoped account token through the existing Worker's
external-CI setup and stored it directly as the GitHub `production` environment
secret. That environment permits only `main`, with no tags. The successful
main-push deployment verifies this credential on the unattended path. No token
value is stored in this repository. For replacement or rotation, preserve
these restrictions:

1. In Cloudflare, select the main account
   `4fe85a31fa782a90b1758694d2314e0a`, then **Manage account → Account API tokens
   → Create Token**. Name it for Evergreen GitHub production deployment.
2. Grant the Workers **Editor** role at the **specific Worker** scope,
   selecting only **`evergreen-website`**. Do not choose all Workers, the
   account-wide legacy Workers Scripts permission, or the consultation/preview
   Workers. Do not add DNS, zone-route, storage, email, or token-management
   permissions. The existing custom-domain binding stays managed separately.
   Editor can deploy code and manage secrets for the selected Worker; it is
   not an assets-only permission. Review the summary before creating the token.
3. In the transferred GitHub repository, open **Settings → Environments →
   production**. Restrict deployment branches to **`main`**. Save the token as
   the environment secret **`CLOUDFLARE_API_TOKEN`**. Paste it directly there;
   do not put it in source files, chat, logs, or a general repository variable.

Cloudflare documents [account-token creation](https://developers.cloudflare.com/fundamentals/api/get-started/account-owned-tokens/)
and [per-Worker Editor permissions](https://developers.cloudflare.com/workers/authorization/workers/).
Deploying a new version of an existing Worker needs Editor; changing its domain
connection would require additional zone permissions and is outside this job.
No Global API Key, broad default token, or Cloudflare GitHub App is required.

The first migration merge removed the old Pages workflow and completed the
actual automatic main-push path. For future changes, verify pull-request checks,
then follow the main-push deployment through its public checks. Compare served
bytes with the downloaded artifact from that exact Actions run: Linux and macOS
builds can produce different CSS hashes, so a separate local build is not the
reference for a CI deployment. Keep the separate staging Worker for previews.
Future rollback redeployments can use a manual run on `main`; changing the
desired source requires a reviewed source revert first. See the migration
status document for final cleanup of temporary migration access and the unused
Cloudflare GitHub App.

## Routing and rollback

Cloudflare's static assets support `404-page` and `auto-trailing-slash` routing.
The `_headers` file supplies preview indexing and response-header directives.
See [static-site routing](https://developers.cloudflare.com/workers/static-assets/routing/static-site-generation/)
and [headers](https://developers.cloudflare.com/workers/static-assets/headers/)
(reviewed November 17, 2026).

The enabled Cloudflare zone rule **Canonical HTTPS apex** redirects HTTP apex
and HTTP/HTTPS `www` to HTTPS apex with status 301, preserving path and query.
The proxied `www` A record points to the documentation address `192.0.2.0` to
bring redirect traffic to Cloudflare; it is not a web-server origin. All three
redirect variants and valid apex TLS have been checked. An initial HTTPS-`www`
522 stopped after propagation; the corrected state was verified on that URL.

Legacy Tyche-path redirects are verified: the root user-site repository serves
redirect files for the 11 old electrology paths after the dedicated project
Pages site was unpublished. All 66 real old-URL checks passed before and after
transfer, browser visits to the old root and Design 09 reached the new domain,
and the Tyche homepage hash remained unchanged. These GitHub-hosted redirects
use **permanent zero-second meta refresh, not HTTP 301**. Retain them and do
not recreate the old repository address or republish the retired project site.
The new site's `_redirects` file does not control requests that reach GitHub.
